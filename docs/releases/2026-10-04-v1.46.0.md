# KneadIt v1.46.0

Date: 2026-10-04
Tag: v1.46.0

## Summary

Each account can now own only one bakery, and billing finds a bakery's owner by a stored link instead of by matching email addresses. Deleting a customer or a bakery is safer, and CI runs faster.

## Highlights

- **One bakery per account** (#1279). Onboarding was open to any logged-in user, so one account could create unlimited bakeries, each with its own database and a new 30-day trial. An account that already has a bakery is now sent to it, and creating a second one is refused with "Your account already has a bakery." A unique database index enforces this even for a double click or two tabs.
- **Bakery owners are now recorded.** No code ever stored `tenants.user_id`, so the link between a bakery and its owner was empty for every bakery created through onboarding. It's now written at signup and backfilled by the migration below.
- **Billing uses that owner link** (#1285, #1286). Trial expiry, Stripe webhooks and bakery deletion used to match `users.email` to the bakery's email. An owner who changed their login email could have a paying bakery's storefront paused, or keep being charged after the bakery was deleted. They now use the stored owner.
- **Free-forever bakeries are left alone** (#1283, #1281). The trial-expiration run no longer pauses their storefront or sends them trial reminders. The unused `subscribed` middleware is removed.
- **Deleting a bakery cancels the owner's subscription** (#1282). It runs to the end of the paid period. If the Stripe call fails, the bakery isn't deleted.
- **Customers with orders can't be deleted** (#1280). Deleting one used to remove their orders too. The bulk delete now skips them and reports them as failures.
- **Last-owner removal is rechecked under a lock** (#1284), so two owners can't remove each other at the same moment and leave a bakery with none.
- **CI** (#1278, #1287, #1289, #1290). The Pest suite runs in parallel (about 5 to 8 minutes instead of 16 to 19) with a 25-minute timeout, the Tests workflow also runs on pushes to `develop`, and the slow test-impact-analysis job is removed. A new test proves the backup download is refused to anyone but a platform admin.

## Database and deployment notes

- **One central migration:** `2026_10_02_120000_add_unique_user_id_index_to_tenants_table`. It runs on the central database only, and the Forge deploy script's `php artisan migrate --force` applies it. In order:
  1. If any user owns more than one bakery, it changes nothing and fails with a clear message listing them.
  2. It links bakeries that have no owner when exactly one user has the same email (case-insensitive). Anything unclear is left unlinked and logged once as `Bakeries without an owner were left unlinked`.
  3. It adds a unique index on `tenants.user_id`. Bakeries without an owner (demo, test and platform-created) are unaffected.
- The `tenants` table is not rebuilt. Only the index is added.
- Production's single bakery already has its owner set, so the migration should change nothing there. After deploying, check the log for the "left unlinked" warning. A bakery without an owner gets no plan syncs and cancels nothing when deleted.
- No tenant migrations. Still add `php artisan tenants:migrate --force` after `php artisan migrate --force` in the Forge deploy script.
- Follow the standard deployment checklist in [Operations](../operations.md#deployment-and-release), including `bin/sync-version` before configuration caching.
