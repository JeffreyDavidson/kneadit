# KneadIt architecture

## System shape

KneadIt is one Laravel application serving two related surfaces:

1. The **central application** serves the marketing site, bakery registration and onboarding, subscription billing, the public bakery directory, and the platform-admin Filament panel.
2. A **tenant application** serves a bakery's storefront, tenant API, customer account flows, and bakery-admin Filament panel.

Both surfaces share application code. The request host and tenancy middleware decide which database context is active.

## Data and tenancy boundaries

The central connection is named `central`. It contains the platform tenant and domain records plus central concerns such as platform settings and subscription state. Every bakery has a separate SQLite database. `config/tenancy.php` uses `TenantSQLiteDatabaseManager`, with files rooted at `TENANT_DB_PATH` or `database_path()` when the variable is unset. `TenantDatabasePath` rejects path separators/traversal, and the manager refuses symlinks before connecting.

Tenancy bootstraps five Laravel facilities:

- The database connection switches to the tenant database.
- cache operations receive a tenant-specific tag.
- the private CSV import and expense receipt disks receive a tenant-specific root.
- queued work carries tenant context through `QueueTenancyBootstrapper`.
- generated URLs point at the bakery through `TenantUrlBootstrapper` (see below).

`TenantUrlBootstrapper` forces the URL root and scheme to the bakery's primary storefront while tenancy is active, so `route()`, `url()` and signed URLs built by the scheduler, queue workers and central panel actions (`withinTenant()`) point at the bakery instead of `APP_URL`, where bakery routes do not exist. `TenantUrlGenerator::primaryStorefront()` picks the URL: the bakery's custom domain when `tenants.custom_domain` is set, `tenants.custom_domain_verified_at` is set (when last checked, the domain reached this application over HTTPS, either directly or through a proxy; see `VerifyCustomDomain` below) and a `domains` row ties it to that bakery, otherwise `{subdomain}.{tenant domain}`. The scheme and tenant domain come from `APP_URL` and `tenancy.tenant_domain`, and a custom domain drops the platform port. The bootstrapper does nothing when the current request is already on a non-central host (the bakery's own subdomain or custom domain), so HTTP requests keep generating URLs on the host the customer is using, and `revert()` clears the override when tenancy ends. Signed bakery links (`signed`, not `signed:relative`) are therefore signed against the same host the customer opens. `MarketingUnsubscribeLinks` builds its host from the same resolver. The "Powered by KneadIt" link in `BaseMailable` uses `APP_URL` directly so it keeps pointing at the platform. Mail the platform sends from outside any bakery (everything in `app/Mail/Platform` except the staff invitation and weekly digest, which run inside a bakery) extends `PlatformMail`, which supplies KneadIt's own branding instead of reading tenant settings, so it renders in a queue worker with no bakery database; whatever the mail passes itself (such as the `storeName` of the bakery it is about) wins. `TenantUrlGenerator::centralAdmin()` builds the platform admin link from `APP_URL`, because the Filament panel's own URL needs a request domain that queued jobs lack. On a developer's machine, `/mail-previews` shows each platform email in the browser with sample data from `PlatformMailPreviews` (models made in memory, never saved; nothing is sent). `EnsureLocalEnvironment` answers 404 for these routes in every other environment, and `PreventAccessFromTenantDomains` keeps them off bakery hosts.

Filesystem tenancy is deliberately scoped to the `imports` and `receipts` disks. Existing local/public asset URLs keep their established behavior, while sensitive imports and receipts cannot cross tenant roots.

Tenant creation runs database creation and tenant migrations synchronously from `TenancyServiceProvider`. Tenant deletion removes the tenant database synchronously. Central migrations live in `database/migrations`; tenant migrations live in `database/migrations/tenant` and are run through `tenants:migrate`.

### Request flow

The global web stack prepends `InitializeTenancyIfNeeded` before session startup:

```text
HTTP request
  -> inspect Host
  -> central domain? retain central connection
  -> tenant/custom domain? identify tenant and initialize tenancy
  -> start session/authentication in the selected database context
  -> route/controller/Filament/Livewire handling
  -> response security headers and actor context
```

The `web` group adds `SecurityHeaders` (frame, content-type, referrer and permissions headers plus the CSP). The two Filament panels have their own middleware stack, so each lists `SecurityHeaders::withoutCsp()`: the same headers minus the CSP, because Filament and Livewire print inline scripts that carry no nonce, which an enforced CSP would block.

Central domains are configured in `config/tenancy.php`; production lists `app.getkneadit.app` (and the staging app hosts) but neither `getkneadit.app` nor `www.getkneadit.app`, while local development uses `app.getkneadit.test` for the application and retains `kneadit.test` as the tenant-development domain. The separate marketing site uses `getkneadit.test`. Tenant routes additionally apply `InitializeTenancyByDomainOrSubdomain` and reject access from central domains. This supports both bakery subdomains and domain records representing custom domains. The app's own `App\Tenancy\Middleware\InitializeTenancyByDomainOrSubdomain` (and `InitializeTenancyBySubdomain`) replace Stancl's: besides hosts ending in a central domain, a host that is exactly `{label}.{tenancy.tenant_domain}` is a bakery subdomain resolved by the `domains` row `{label}`, so the tenant domain does not need to be a central domain (in production it is not). A bakery's subdomain is stored in `tenants.subdomain` and is separate from its id (the primary key, tenant database file name, storage paths and foreign keys never change): `TenantUrlGenerator` builds every bakery link from `{subdomain}.{tenant domain}`, falling back to the id only when `subdomain` is null; onboarding sets both to the same value. `ChangeTenantSubdomain` (used by the central bakery Edit page's **Change subdomain** action, platform admins only, and by `php artisan tenants:change-subdomain {tenant} {subdomain}`) validates with the onboarding rules (`StoreOnboardingRequest::subdomainRules()`: format, reserved list, and uniqueness against every `domains` row and every tenant id and subdomain, except the bakery's own), adds the new dot-less `domains` row, sets `tenants.subdomain` and keeps the old row, so it is idempotent and old links still resolve. The middleware answers a GET or HEAD request on an old subdomain (the host's label is not the tenant's current `subdomain`) with a 301 to the same path and query on the current subdomain; other methods proceed unchanged so in-flight form posts are not lost, and custom domains are never redirected. Absolute signed links minted for the old subdomain fail their signature after the redirect, because the signature covers the host. If a `domains` row already holds the full host it is resolved as a domain, as before; deeper hosts such as `a.b.{tenant domain}` and unrelated hosts are resolved as custom domains and 404 when unknown. `AddCustomDomain` normalizes a bakery's custom domain and rejects, with a validation error, anything that is not a valid hostname, is a central domain or a subdomain of the tenant domain, or already belongs to another bakery; replacing a domain releases the old record and Forge alias. A new or replaced domain starts unverified (`AddCustomDomain` and `RemoveCustomDomain` clear `custom_domain_verified_at`). `VerifyCustomDomain` asks `CustomDomainService::verify()` for a `DomainCheck` (`Verified`, `VerifiedThroughProxy`, `DnsMissing` or `HttpsUnavailable`). Ownership is proven by the `HttpsProbe` contract (`HttpHttpsProbe`: `GET https://{domain}/.well-known/kneadit-domain-proof`, certificate checked, no redirects followed, 5 s timeout, constant-time comparison; faked in tests with `fakeDnsRecords()` and `fakeHttpsProbe()`). The proof is `CustomDomainProof`, an HMAC-SHA256 of the requested host keyed with `APP_KEY`, served by `DomainProofController` on any host with a `domains` row (outside the storefront-enabled check, so a paused storefront keeps answering; `Cache-Control: no-store, private`; 404 on central domains), so a proof for one host never verifies another. Two paths verify a domain: **direct** (DNS from the `DnsResolver` contract, `PhpDnsResolver` in production, equals the server IP and the proof passes; DNS right but no proof is `HttpsUnavailable`) and **proxied** (the A record is not the server IP, as with Cloudflare's proxy, but the proof still passes: `VerifiedThroughProxy`). A domain that is neither pointing here nor answering with the proof is `DnsMissing`. No Cloudflare API call or IP-range detection is involved. The timestamp is set when either path passes and cleared otherwise. The Settings → Custom Domain page runs it on load, on save and on "Verify domain", shows the DNS and HTTPS parts separately, and offers **Request SSL certificate** (Forge) when DNS is right but HTTPS is not; the daily `tenants:verify-custom-domains` command re-checks every bakery with a custom domain, clearing the timestamp (and logging the reason, `dns` or `https`) when a domain stops qualifying. In the central panel the bakery form shows the custom domain read-only (disabled, never saved from the form) with its verification status; platform admins change it from the **Set custom domain**, **Remove custom domain** and **Verify domain** and **Request SSL certificate** actions on the bakery's Edit page, which call `AddCustomDomain`, `RemoveCustomDomain` and `VerifyCustomDomain`, so the admin panel gets the same validation, `domains` row, Forge alias and verification reset.

An unknown tenant domain returns 404. If a central tenant record exists but its SQLite file does not, local development recreates and migrates it automatically. Production returns 503 and instructs the operator to run `php artisan tenants:doctor --fix`.

The root URL is deliberately universal: the global middleware establishes central or tenant context once, then `RootController` serves the platform landing page or bakery storefront without re-running tenancy middleware.

### Route organization

`routes/web.php` is the central route composition entry point. It loads:

- `routes/central/auth.php` for platform-user registration, login, email verification, and password reset. Staff emails are matched without regard to case: the `users` provider is `App\Support\Auth\NormalizedEmailUserProvider`, which tries the exact email first and then compares `lower(email)` with the normalized input, so sign-in (including the Filament panels) and password-reset lookups find accounts stored before emails were normalized. `RegisterRequest` normalizes `email` and rejects one that matches an existing account's lowercased email, and `CreateUser` stores it normalized. Existing mixed-case rows are not rewritten. The forgot-password form always answers "If an account exists for that email, we've sent a reset link." (only a throttled request shows its own message), and a completed reset rotates the remember token.
- `routes/central/platform.php` for onboarding, platform-admin exports, backups, maintenance previews, and impersonation.
- `routes/central/marketing.php` for the central landing page, legal pages, directory, blog, referrals, contact, and CSP reports.
- `routes/central/seo.php` for the sitemap and robots response.
- `routes/billing.php` for subscription billing and Stripe webhooks.

Central-only routes carry `PreventAccessFromTenantDomains`, which answers 404 on any host outside `tenancy.central_domains`, because the web group has already put a bakery in context on its own host and these routes read the central database. That covers platform accounts and onboarding (`auth.php`, `platform.php`), the marketing site, blog, directory, referral and contact routes, the sitemap and robots response, the admin export, backup, maintenance-preview and impersonation URLs, and `/billing`. Three routes deliberately answer on bakery hosts: `/` (`RootController` serves the bakery storefront), `login` (the redirect that signed-out visitors are sent to) and `logout`; `csp.report` also stays open because every page's CSP reports to its own host. `tests/Feature/Routing/CentralRoutesHostTest.php` walks every route served by a Central or Billing controller and fails if one answers on a bakery host without being on its allowlist. A tenant `users.role` created without an explicit role is `staff` (tenant migration `2026_10_06_120000`); code that creates a bakery's first user sets `UserRole::Owner` itself (`ProvisionTenantOwner`, the demo and test tenant commands, `DatabaseSeeder`, and `CreateUser` for the platform account).

`routes/tenant.php` is the tenant route composition entry point. Its outer group owns tenant initialization and central-domain protection before loading:

- `routes/tenant/access.php` for PWA metadata, invitations, tenant impersonation consumption, driver links, campaign previews, and Stripe Connect.
- `routes/tenant/admin.php` for authenticated tenant admin utilities such as invoices, product labels and expense receipts.
- `routes/tenant/storefront.php` for public bakery content and storefront commerce.
- `routes/tenant/account.php` for customer account authentication, profile, orders, and email verification.
- `routes/tenant/orders.php` for checkout, order access, payment callbacks, cart, capacity, and order-related AJAX endpoints.
- `routes/tenant/api.php` for tenant JSON endpoints, split into read and write throttle groups. The resources are JSON:API resources that load whatever `?include=` names, so each controller eager-loads the relations it exposes with the storefront's filter (active products, approved reviews); a relation loaded that way is not re-queried by the include, so an inactive product cannot leak. `/api/menu` always includes its products. `/api/capacity/{date}` validates the date as `Y-m-d` (422 otherwise). There is no public review submission endpoint: `GET /api/reviews` lists approved reviews only, and reviews are written through the signed per-order review link.

Routes that access tenant models belong under the tenant loader, even when their controllers are used by an admin-facing page. This keeps route middleware, model binding, and database tenancy context aligned.

### HTTP controller organization

HTTP controllers are grouped first by application surface and then by concern:

- `app/Http/Controllers/Central/` contains platform-facing controllers. `Auth/` and `Onboarding/` hold the central authentication and signup lifecycle; other controllers remain at the central surface root when they span a single platform concern.
- `app/Http/Controllers/Tenant/` contains tenant-bound controllers. `Storefront/` owns public bakery pages and customer account flows, while `Admin/`, `Api/`, `Catering/`, `Invitations/`, `Marketing/`, and `Orders/` make their route surface explicit.
- `app/Http/Controllers/Billing/` and `app/Http/Controllers/Stripe/` are provider or subscription boundaries. They may invoke domain actions but do not define tenant presentation ownership.

The controller namespace should match the route surface and the mirrored `tests/Feature/Http/Controllers/` path. New tenant controllers belong under `Tenant/<Surface>/`; do not add new top-level tenant controller directories.

## Application layers

KneadIt favors explicit Laravel boundaries rather than a generic service/repository layer:

- **Controllers and Filament pages** coordinate HTTP/UI behavior and remain thin.
- **Form Requests** validate and translate request data.
- **Actions** under `app/Actions/<Domain>` own writes and business transitions. They are generally invokable and container-resolved.
- **Queries** and custom Eloquent **Builders** own reusable read behavior.
- **Services** integrate external systems or encapsulate cohesive computations and orchestration.
- **DTOs and value objects** carry validated shapes and domain values.
- **Events/listeners** handle consequences that follow a completed domain action.
- **Policies and gates** enforce model and platform authorization.
- **Presenters/ViewModels/components** shape complex output where the view earns a separate boundary.

Models, actions, services, enums, builders, queries, policies, factories, and tests are grouped by domain. Tests mirror the `app` structure across the applicable unit, integration, and feature suites.

Application-wide framework wiring is split by responsibility in `app/Providers/`: `ApplicationBindingsServiceProvider` owns container bindings, `InfrastructureServiceProvider` owns queue, cache, tenancy, and payment infrastructure hooks, `RateLimitServiceProvider` owns named throttles, and `AppServiceProvider` owns application features and UI hooks. Keep new bootstrapping in the narrowest provider rather than expanding a catch-all provider.

Shared test setup follows the same rule: `tests/Pest.php` keeps suite-wide lifecycle configuration, while domain or environment-specific fixtures belong in named files under `tests/Support/Bootstrap/` or `tests/Support/`. Tenant database cleanup is implemented there so feature and integration tests do not each need to know which persistent browser fixtures must be preserved.

  Half-built platform features are hidden, not deleted: the Maintenance Mode and Feature Usage pages and the Announcements resource return 403 and have no navigation entry (`canAccess()` / `canViewAny()` return false), and the Activity page offers only the Admin Actions tab (`hasPlatformEventsTab()` is false). Each carries a comment naming what has to be built before it comes back.

- **Orders:** carts, checkout, capacity and stock validation, discounts, fulfillment, order messaging, tracking, invoices, payment state, and refunds.
- **Inventory and production:** products, categories, ingredients, recipes, suppliers, stock adjustments, waitlists, seasonal items, and production planning.
- **Customers and engagement:** customer profiles, favorites, notes, referrals, loyalty, campaigns, surveys, reviews, reminders, contact messages, and catering inquiries.
  The storefront Rewards page (`LoyaltyController`) shows a customer's points only to the signed-in customer with a verified email (the `customer.verified` middleware on the route); signed-out visitors see the program and a sign-in link that returns them to the page, and there is no lookup by email. Bakery-side, the gift card preset and default amounts are hidden from Manage Settings (stored, but the storefront does not read them), and the Referral Program page shows the share link, referral count and referral list but makes no free-month promise, because nothing grants the reward.
  Email campaigns have two separate paths. Bakeries email their own customers with customer campaigns (`CustomerCampaign` and `SendCustomerCampaign`, stored in the tenant database and managed in the bakery-admin panel). Platform email campaigns (`EmailCampaign`, stored centrally and managed only in the central panel) go to bakers: `SendEmailCampaign` picks the bakeries in the campaign's segment (All, Starter, Growth, Pro, Trial or Inactive; All and the plan segments skip paused bakeries, and Inactive is the paused ones), emails each bakery's owner address (`tenants.email`, lowercased) once using `PlatformCampaignMail`, and records the unique count as `recipient_count`. It never enters a tenant database and throws `PlatformCampaignContextException` if called inside a tenant context. Both senders write a log row per recipient before emailing (`customer_campaign_logs` or `email_campaign_logs`, unique on campaign and email), so a retried send skips everyone already logged and never emails a recipient twice; a crash between the log row and the email loses that one email. Scheduled campaigns go out every 15 minutes: `campaigns:send-scheduled` (per tenant) and `platform:send-scheduled-campaigns` (central) claim a due campaign atomically (Scheduled to Sending), and reset one stuck in Sending for over an hour to Scheduled (giving a "Send now" campaign a `scheduled_at` of now) so it resumes.
- **Financial:** income, expenses, coupons, gift cards, refunds, reporting, tax export, Stripe, and PayPal.
- **Operations and staff:** schedules, blocked dates, holidays, capacity, check-ins, staff invitations and roles, activity logs, and webhook delivery.
- **Analytics:** page and product-impression records use a keyed, pseudonymous visitor identifier. Raw network/device identifiers are not persisted, recording failures are reported without breaking storefront responses, and scheduled tenant-wide retention bounds stored history.
- **Storage:** intentionally public assets remain on the established `public` disk. Sensitive CSV imports and expense receipts use dedicated private disks that are neither directly served nor shared across tenant roots; receipts are shown through `admin.expenses.receipt` (`ShowExpenseReceiptController`, `can:view,expense`, so Manager and above, plus the same `growth-features` plan check as `ExpenseResource`), which falls back to the public disk for receipts uploaded before the private disk existed; all configured disks fail loudly on storage errors.

## Order lifecycle

Storefront requests are validated by `StoreOrderRequest` (the API uses `StoreApiOrderRequest`) and converted to `CreateOrderData`. Both requests apply `ProductAvailableOnDeliveryDate` to each item: a product with seasonal windows can only be ordered for a delivery date inside one of them (inclusive), and products with no windows are always available (`ProductQueryBuilder::availableOn`). `CreateOrder` then executes a database transaction containing an ordered Laravel pipeline:

1. Calculate totals and enforce the minimum order amount. Delivery is priced from the bakery's Delivery Fee Tiers setting (`delivery_tier` is the tier's position) and is free once the subtotal reaches the free-delivery minimum; delivery orders are rejected when delivery is turned off.
2. Validate date capacity and stock availability.
3. Apply sitewide sales, coupons, gift cards, referrals, and tier perks.
4. Resolve the customer and persist the order.
5. Record coupon/gift-card/referral effects and persist line items.
6. Mark the cart converted.

Customer referrals follow the order through its lifecycle. `ApplyReferral` discounts only new customers: an email with a prior non-cancelled order, or an already-referred customer whose referral wasn't cancelled, gets no discount. `PersistReferral` records the referral as Pending and fires nothing. When the order is delivered, `CompleteCustomerReferralListener` marks it Completed and fires `CustomerReferralCompleted`; when the order is cancelled, `CancelCustomerReferralListener` marks it Cancelled and no reward is issued. `SendCustomerReferralRewardEmailListener` mails the referrer's coupon, which `RewardReferrer` creates at most once per referral (a repeated event or retried job reuses the existing coupon).

If capacity rejects the request, the pipeline returns no order. If no cart line is orderable (every product was deactivated or removed since the cart was built), `CalculateOrderTotals` throws `NoOrderableItemsException`, so the customer is told to review the cart instead of that the date is full. Other domain validation failures return targeted form errors. A successful transaction logs the placement and emits `OrderCreated`. The current session is granted access to the resulting order before redirecting to payment or confirmation.

Staff quick orders skip this pipeline: the Quick Order form (`QuickOrderForm`) offers a Delivery Distance select built from the same Delivery Fee Tiers, and `CreateQuickOrder` prices delivery with `OrderSettings::deliveryFee()`. A bakery with no tiers configured gets a free-delivery quick order. `CreateQuickOrderData` takes the payment method and delivery type as enums (the form's selects hand back enum instances), and the order stores the chosen delivery type. `QuickOrder::createOrder()` reports any exception before showing the generic error notification. Every quick order needs a customer email, like storefront orders, because `orders.customer_id` is required and customers are keyed by email; an existing customer with that email is reused.

The storefront order form (`order-form-script.blade.php`) submits with `fetch` and `Accept: application/json`, so a `StoreOrderRequest` failure comes back as a 422 `{message, errors}` body. The script keeps the first error per field in `fieldErrors`, shows it under the matching input (`x-storefront.order-field-error`, with `items.*` errors shown in the cart summary), clears it when that field changes, and puts the response `message` by the submit button. `SubmitOrderController` throws the order pipeline's domain failures (minimum order, stock and no-longer-available items under `items`, a full date under `delivery_date`, a taken pickup slot under `delivery_time`) as `ValidationException`s, so the fetch form gets the same 422 body and a plain form post redirects back with the errors and old input. Other failures keep the generic message.

### Order access and tracking

Order-by-number routes (`order.access` middleware, `EnsureOrderAccess`) require `OrderAccessGuard::canAccess()`: a logged-in customer with a verified email who owns the order, or an order number the session has been granted. A session is granted an order by placing it, returning from Stripe, passing `VerifyOrderAccessController` (order number plus matching email), or opening a tracking link.

The tracking form (`POST /track`) only emails a link and never shows orders. `TrackingController::store` always redirects back with the same "check your email" message (page content key `link_sent_message`), whether or not the address has orders. When it does, it queues `OrderTrackingLinkMail` to that address, at most one per customer every five minutes (`RateLimiter`). The mail holds a 30-minute `URL::temporarySignedRoute` to `GET /track/access/{customer}` (`order.track.access`, `signed` middleware). `ShowTrackedOrdersController` renders the order list for that customer and grants the session access to each order.

Customer accounts: `RegisterCustomer` creates a customer, or claims an existing guest customer row with the same email (no password yet). A claim sets the password and clears `email_verified_at` but keeps the row's existing name and phone (blanks are filled from the form), and the customer is logged in straight away. Until the email is verified, the `customer.verified` middleware (`EnsureCustomerEmailIsVerified`) redirects `account`, `account/orders` and `account/profile` (GET and POST) to `account.email.verify.notice`, and returns 403 JSON on the favorites API (`api.favorites.index` and `api.favorites.toggle`). The verify notice, verify link, resend and logout stay reachable. The same rule applies to `OrderAccessGuard::canAccess()`: the customer-owns-order shortcut needs `hasVerifiedEmail()`. Session grants (just-placed order, Stripe return, order verify page, tracking link) are unaffected.

A customer password reset ends every other signed-in session for that customer. `ResetPasswordController` sets the password, rotates the remember token and fires `PasswordReset`. Laravel's `AuthenticateSession` only watches the default (staff) guard, so `AuthenticateCustomerSession` does the same for the `customer` guard on all tenant routes: a `Login` listener in `AuthServiceProvider` records an HMAC of the password hash in the session at sign-in (including a remember-cookie login), and a session whose recorded hash no longer matches the customer's password is invalidated and carries on as a guest, so `auth:customer` routes redirect to the login page. The middleware is placed ahead of `auth` in the middleware priority list (`bootstrap/app.php`) so it runs before `auth:customer` decides. A session with no recorded hash (one that predates this check) adopts the current hash on its next request.

Customer emails are matched case-insensitively. SQLite compares text case-sensitively, so `Bob@x.com` and `bob@x.com` would otherwise be two customers. `App\Support\EmailAddress::normalize()` (lowercase and trim) is the single definition. On write, `App\Casts\EmailAddressCast` stores `customers.email` and the other customer email columns lowercased: `carts`, `customer_favorites`, `waitlist_entries`, `product_waitlists`, `customer_campaign_logs`, `customer_photos`, `reviews`, `survey_responses` and `catering_inquiries` (`customer_email`). On read, the builder methods (`CustomerQueryBuilder::forEmail()`, `OrderQueryBuilder::placedByEmail()` and `forCustomerEmail()`, `CustomerFavoriteQueryBuilder::forCustomer()`) normalize their input, so callers pass the email as typed. Eloquent casts do not apply to `where` values, so the call sites that use `updateOrCreate`, `firstOrNew` or `CartManager::updateContact` (`ResolveCustomer`, `RegisterCustomer`, `JoinProductWaitlist`) normalize explicitly, and the storefront login, forgot-password and reset-password requests normalize `email` in `prepareForValidation()` before the auth guard and password broker look the customer up. The admin customer form validates uniqueness on the normalized email. The `2026_10_01_140000_normalize_customer_email_case` tenant migration lowercases existing rows. It leaves rows that would collide untouched and logs a warning with the tenant id and the row ids and emails: customers whose emails differ only by case (`customers.email` is unique), and favorites of the same product. Those rows have to be merged by hand.

### Customer order edits

While the modification window is open, customers can change quantities and the tip on a pending, unpaid order (`ModifyOrder`). An order with a Stripe checkout session (`stripe_checkout_session_id`) cannot be edited until the payment settles, because the open session would still charge the old amount (`OrderModificationGuard::hasOpenCheckout()`). The order is re-priced inside the same transaction. `orders.original_subtotal` and `original_discount_amount` hold the values at placement (filled by `PersistOrder`, or on first edit for older orders). The aggregate discount is rescaled from them by `ModifiedOrderPricing`, never above the original, so undoing an edit restores it exactly. The coupon `Usage` transaction is scaled by the same proportion. The gift card draw is capped at what is left to pay and never grows; any unused part is credited back to the card and subtracted from the order's `Redemption` transaction, so a later cancellation (`ReverseOrderDiscounts`) refunds exactly the reduced amount (`AdjustOrderDiscountLedgers`). Delivery is not re-priced because the tier is not stored; an edit that lowers the subtotal below the pickup or delivery minimum, or below the free-delivery minimum for an order that qualified for free delivery, is rejected with `OrderNotModifiableException`.

### Deleting orders

Orders are hard-deleted (no soft deletes), and deleting cascades to the order's refunds and messages, so deletion is restricted to orders nothing financial happened on. `OrderDeletionGuard::canDelete()` allows it only when the status allows deletion (`OrderStatus::allowsDeletion()`: Pending or Cancelled), the payment status allows it (`PaymentStatus::allowsDeletion()`: Unpaid or Cancelled), and the order has no refunds. `OrderPolicy::delete()` additionally requires the Manager role or above; staff cancel instead. Every other order is cancelled, which keeps the record. The Orders table's bulk delete skips orders the policy denies and the notification says how many were not deleted. `OrderObserver::deleting()` runs `ReverseOrderDiscounts` before the row goes, so the coupon use and gift card draw are given back the same as on cancellation (idempotent, so an order that was already cancelled is not reversed twice).

### Deleting products and categories

Past orders keep their lines. `ProductPolicy::delete()` refuses a product that is on any order (`order_items`) or has reviews (a review keeps no copy of the product name), and `CategoryPolicy::delete()` refuses a category that still has products. Both return a denying `Response` naming the record and pointing to Deactivate (`is_active`, a toggle in each table), and Filament's `AuthorizedDeleteBulkAction` shows those messages for the records a bulk delete skipped. `RolePolicy::delete()` is typed `bool|Response` for this. The database enforces the same rules if something bypasses the policy: `order_items.product_id` is `ON DELETE SET NULL` (the line stays, with its `name`; the migration copies product names onto lines that had none), and `products.category_id` is `ON DELETE RESTRICT`. `reviews.product_id` is still `ON DELETE CASCADE`; the policy is its only guard. Order lines created today do not yet copy the product name, so only lines present when the migration ran have the snapshot.

### Ingredient units and stock

An ingredient has a stock unit (`ingredients.unit`), and each linked recipe line (`recipe_ingredients.unit`) has its own. Both come from the `MeasurementUnit` enum, which knows each unit's dimension (`UnitDimension`: mass, volume or count) and its factor to the dimension's base unit (grams, millilitres, each), so `MeasurementUnit::convert()` converts within a dimension and returns null across dimensions. The columns stay plain strings so a legacy value that isn't a known unit still displays; `Ingredient::measurement_unit` resolves it to the enum or null.

Everything that compares or moves stock goes through `RecipeLineConverter::inStockUnit()`, which expresses a recipe line's quantity in the ingredient's stock unit at full precision: the stock check (`IngredientDemandCalculator`, used by `ValidateStockAvailability` and `CheckOrderStockAvailability`), the Baking deduction and cancellation restock (`AdjustOrderIngredients`), and the upcoming-order needs in `ShoppingListService`. Stock and recipe quantities (`ingredients.current_stock` and `low_stock_threshold`, `recipe_ingredients.quantity`, `stock_adjustments.quantity`) are `decimal(12,4)`, so a 1 g draw from stock held in kg (0.001) isn't lost. The stock check compares at 4 decimals and `AdjustOrderIngredients` rounds the converted amount to 4 decimals at write. The UI shows stock to 2 decimals unless that would show a small amount as 0 (`StockQuantity::display()`), and editable fields keep every stored digit (`StockQuantity::input()`). A line that can't be converted (different dimensions, or an unknown unit) is skipped with a logged warning rather than blocking the order. A recipe's linked lines live in the `recipe_ingredients` table, which is read two ways: `Recipe::inventoryIngredients()` (a BelongsToMany with the quantity and unit as pivot columns) feeds deduction, demand and labels, and `Recipe::ingredientLines()` (a HasMany over the `RecipeIngredient` model) is what the recipe form's relationship repeater saves, since Filament's repeater can only create and update rows of a HasMany. The product label (`ProductLabelPresenter`) lists a recipe's linked ingredients by weight, heaviest first: it converts each mass-unit line to grams with `MeasurementUnit`, keeps equal weights in entry order, and puts lines in volume, count or unknown units after the weighed ones in entry order, since those can't be weighed without a density. `hasUnweighedIngredients()` drives a screen-only note on the label page that the order is approximate; the printed label carries no warning. The Label Generator tool page builds its ingredients, "Contains:" line and the same screen-only note from `ProductLabelPresenter` too (eager-loading `recipe.inventoryIngredients`), truncating the ordered list rather than the recipe's free-text JSON. The form rejects linking the same ingredient twice on one recipe. `RecipeForm` limits a linked line's units to the selected ingredient's dimension and shows a warning hint on a saved line that no longer fits.

### Product waitlist

The storefront menu offers a waitlist for inactive products only; `StoreProductWaitlistRequest` rejects joining for an active product ("This item is available now."). When a product's `is_active` changes from false to true, `ProductObserver` dispatches `ProductReactivated` after the transaction commits. The queued `NotifyProductWaitlistListener` runs inside the dispatching tenant and calls `NotifyProductWaitlist`, which queues one `ProductAvailableMail` per un-notified entry and stamps `notified_at`. It sends nothing for an inactive product, and nothing (leaving entries waiting) when the tenant's `product_available` email toggle is off. The admin "Notify Waitlist" row action is a manual resend for active products.

### Date capacity

`CapacityCalculator` decides how many active orders a delivery date can take. Both it and the storefront availability calendar (`AvailabilityService`) read the rules through `DateCapacityRules`, which loads everything for a date range in four queries. A date is unavailable when it is closed (an all-day `BlockedDate`, a closed day in Schedule Manager, or an active holiday whose `order_deadline` has passed; the deadline day itself stays open), or when its orders reach the max. Staff-created orders (quick orders, catering conversions) skip this check. The max comes from the first level that sets one, most specific first:

1. Capacity limit for that exact date
2. Active holiday on that date
3. Capacity limit for that weekday
4. Schedule Manager max orders for that weekday
5. Tenant default (`default_daily_capacity`)

A blocked capacity limit sets the max to 0. A blank or 0 max means "no limit here" and falls through to the next level.

### Earliest delivery date

`EarliestDeliveryDate` decides the first delivery date a customer can choose: the bakery's local today (the `timezone` order setting, UTC until set) plus the lead-time days (`minimum_order_lead_hours`, rounded up to whole days). If today's Schedule Manager order cutoff has passed, the order counts as placed tomorrow, so the date moves back one day. The storefront and API order requests validate against it, and the order page shows it and uses it as the date picker's minimum. Staff-created orders don't use it.

"Today" for all of these rules is the bakery's local date from `BakeryClock` (the same `timezone` setting). `BakeryClock::today()` returns that date as a plain date value, so it compares directly with date columns. `BakeryClock` resolves the current tenant's settings on every call, so a clock injected before a scheduled command enters a tenant (the birthday and repeat-order engagements) still follows each tenant's timezone; `TenantSettings` is bound per resolve (cached in `TenantSettingsRegistry`, which `TenancyManager` flushes on every tenant switch) rather than scoped, so it can never keep a previous tenant's values. The holiday deadline check, the availability calendar, the capacity dashboard widget, upcoming holidays and the holiday deadline/day counts in admin all use it. Customer engagement uses it too: the birthday email and `BirthdayCalculator` match birthdays against the bakery-local date, and repeat-order reminders measure their cutoff, days since the last order and next reminder date from it. Timestamps such as `reminder_sent_at` stay UTC. The orders dashboard widgets (today's orders, upcoming orders, baking sheet, revenue chart) and the stats overview query, including its week boundaries, use it as well. Timestamp series bucket by the bakery-local day too: the stats overview's pending orders and storefront views and the storefront analytics daily trend use `DateCountQuery::countByLocalDay()`, which turns each local day into a `[start, end)` range of UTC instants and counts them in one query (SQLite and MySQL alike), while the original `DateCountQuery::count()` still groups by UTC date for the central platform stats. The birthday widget's cache key includes the bakery-local date, so `days_until` never survives local midnight. The scheduled customer and baker sends (birthday emails, repeat-order reminders, the weekly digest and low-stock alerts) also run on the bakery clock: the scheduler fires them hourly and `LocalSendWindow` lets each tenant through only at its local send hour, once per local date (see `docs/operations.md`). The weekly digest's "last week" and "upcoming" are the bakery-local Monday to Sunday weeks (`WeeklyDigestDataCollector` uses `BakeryClock`, converting the week bounds to UTC for new customers' `created_at`; the digest's orders and revenue are the revenue orders delivered that week). The repeat-order reminder is based on the customer's latest order that isn't cancelled or refunded, whatever its payment status, so an open unpaid order suppresses it.

The storefront analytics page and the storefront views widget turn bakery-local day and week boundaries into instants in the app timezone before comparing them with `created_at`. Seasonal item availability (the `current`, `upcoming` and `expired` builder methods and `is_currently_available`), the birthday widget, and the Quick Order date picker's minimum date also use the bakery's local today. Gift card expiry is an inclusive bakery-local date: `GiftCardStatus::resolve()` and the `usable()` / `expired()` methods on `GiftCardQueryBuilder` compare `expires_at` with `BakeryClock::today()`, so a card works through the end of its expiry day. The coupon form's `starts_at` and `expires_at` pickers use the bakery timezone (values are stored in the app timezone), and so do the customer campaign form's `scheduled_at` and the blog post form's `published_at`, so the scheduler and the published scope (which compare app-timezone instants) fire at the time the baker typed. `PickupSlotResolver::availableSlots()` drops slots that start before bakery-local now when the requested date is the bakery's today, and the catering event-date minimum comes from `BakeryClock::today()` in both the form and `StoreCateringInquiryRequest`. Birthday coupons (`CreateBirthdayCoupon`) get a random `BDAY-` plus 8-character code and record the `customer_id` and bakery-local `birthday_year` they were minted for (unique together), which is what keeps the action to one coupon per customer per year; the code carries no customer data.

Admin page and form date defaults use the bakery-local date from `BakeryClock::today()` as well: the baking sheet, delivery route planner, weekly prep planner, order calendar and social calendar (including their today markers), the shopping list pages, reorder reminders, the catering event date minimum, the customer birthday maximum and the expense and income date defaults. The reports center's date range and year, the finance summary and tax export year, the product trends month, the label generator's best-by date and the holiday planning calendar's year follow it too. The customer insights widget's week and month turn their bakery-local boundaries into app-timezone instants (`DateRange::inAppTimezone()`) before querying timestamp columns; the goal tracker's month and year are revenue figures, so they use bakery-local dates against `delivery_date` (see Revenue and platform metrics). Every `DateRange` factory (`fromStrings`, `thisWeek`, `thisMonth`, `thisYear`, `lastDays`, `forMonth`) builds its boundaries in the bakery timezone from `BakeryClock`, so a range reads as the bakery's calendar days when compared with a date column such as `delivery_date` (the sales and product reports, the top products and weekly revenue widgets). Queries on timestamp columns call `inAppTimezone()` first: the customer report's new customers and acquisition by month (the months themselves are the bakery-local month of `created_at`, not the UTC month), and the product trends service's `orders.created_at`. The weekly prep planner loads a week's orders with `whereDate` comparisons, so the last day's orders are kept on SQLite as well as MySQL. The reorder reminders page builds its "email customer" link in `ReorderReminders::reminderMailto()` from `TenantSettings->store->name`, and an arch test (`tests/Arch/TenantSettingsPropertiesTest.php`) checks that views only read properties that exist on `TenantSettings`.

All money columns are integer cents. Eloquent models use the project's money cast/value object; raw aggregates and direct database operations bypass casts and must explicitly preserve cents. The `ingredient_supplier` pivot is no exception: `IngredientSupplier` (used by `Supplier::ingredients()` and `Ingredient::suppliers()` through `->using()`) casts `unit_price` and `minimum_order` with `MoneyCentsCast`, so attaching or editing takes dollars from the form and stores cents, and `ShoppingListService` reads them as `Money`. The tax export's expenses and income use `ExpenseQueryBuilder::inDateRange()` and `IncomeQueryBuilder::inDateRange()` (`whereDate`), because `date` columns are stored with a midnight time and a plain `Y-m-d` upper bound would drop the last day.

### Revenue and platform metrics

**Bakery revenue** has one definition, `OrderQueryBuilder::revenue()`: orders whose payment status is Paid (part-paid, unpaid and refunded orders never count) and whose status is not Cancelled, dated by `delivery_date` (a bakery-local date). `revenueInDateRange()` and `revenueInYear()` add the date filter. Every revenue figure starts from it: the dashboard stats, revenue charts and top products (`RevenueQuery`, `ProductSalesQuery`), the Sales report, the Financial report and Finance Summary (`FinancialCalculator`), the goal tracker, the weekly digest (orders, revenue and average order value are the revenue orders delivered last week) and the tax export (both the orders list and the summary, filtered and dated by delivery date, so the "Delivery Date" column and the totals match the other reports). The same orders therefore give the same total on every screen. Customer spend and lifetime value use it too: the customer table's lifetime value and average order, the RFM metrics, the customer report's top customers and repeat rate, the customer directory page's per-customer total spent, the customer detail panel's total spent and average order (`CustomerIntelligence` / `CustomerPresenter`), the reorder reminders' total spent, the customer directory stats, the product report, the weekly digest's top products, and the platform tenant overview's revenue (undated ones are lifetime totals; dated ones use `delivery_date`). `paidInMonth()` and `paidInDateRange()` no longer exist; use `revenueInDateRange()`. The customer insights average order value divides cents correctly (`CustomerInsightsQuery` returns `Money`).

**Platform MRR and trial metrics** (`PlatformRevenueMetricsQuery`, used by the central `PlatformStats` and `RevenueOverview` widgets) come from the owners' Cashier `default` subscriptions, not from `tenants.plan`:

- **MRR** is the sum, priced by each subscription's Stripe price (`SubscriptionTier::fromPriceId()`), of valid (`valid()`) subscriptions that are past any Stripe trial, for bakeries that are not `free_forever`, not `is_demo` and not paused (`paused_at`). **ARPU** is MRR divided by the number of those subscriptions; the chart repeats the sum at each month end for subscriptions that had started by then.
- **Churned** (last 30 days) is a bakery whose owner's subscription ended in the period and who has no paying subscription now, or a bakery paused in the period after its trial ended. **Churn rate** is churned divided by churned plus currently paying bakeries.
- **Trial conversion** is, among bakeries whose trial has ended (not comped, not demos), the share whose owner now has a paying subscription. The central Analytics page (`TenantSubscriptionAnalyticsQuery`, `TenantAnalyticsSummaryQuery`) takes its Active Subscriptions, converted and expired figures from these same metrics, not from the tenant columns.

Report CSVs: the Reports Center builds its file in the browser, so `ReportsCenter::exportCsv()` sanitizes the report payload with `CsvValueSanitizer::deep()` first (formula starters `=`, `+`, `-`, `@`, tab and carriage return get a leading `'`, as in the server-side exports). The central CSV export (`CsvExportService`) writes money columns as dollars.

### Payment paths

The application has two distinct Stripe concerns:

- **SaaS billing:** Laravel Cashier handles bakery subscriptions through central `/billing` routes and `/stripe/webhook`.
  Billing is enforced by pausing the bakery. `tenants.paused_at` (nullable timestamp, `Tenant::is_paused`) says a bakery is paused; `tenants.storefront_enabled` keeps only its onboarding meaning, whether the bakery uses a KneadIt storefront at all (`false` plus `external_website` sends visitors to the bakery's own site). The storefront onboarding step counts as done for either case (`Tenant::storefront_set_up`, used by `TenantOnboardingMetrics`, `TenantHealthService` and `TenantComparisonQuery`). The scheduled `platform:check-trial-expirations` command (`ProcessTrialExpirations`) sends reminders 7, 3 and 1 days before `tenants.trial_ends_at` and, once the trial has passed and the owner (`Tenant::owner()`, linked by `tenants.user_id`) has no valid `default` subscription, runs `PauseTenant` (`paused_at = now()`), for every non-free-forever bakery (Pause is the only on/off switch: the old `tenants.is_active` column is still in the database but nothing reads or writes it), with or without a KneadIt storefront (`TrialExpirationReader::tenantsExpired()` selects `paused_at IS NULL`). A paying owner whose renewal fails (Stripe status `past_due`) keeps the bakery running for `kneadit.past_due_grace_days` (7) after the first failed renewal; `OwnerSubscriptionsQuery::inPastDueGrace()` reads that moment from the subscription row's `updated_at`, which Cashier touches when Stripe moves it to `past_due`. After that the run pauses the bakery. An owner who has ever had a `default` subscription, in any status, is never sent the "trial expired" email (`OwnerSubscriptionsQuery::hasEverSubscribed()`), because Stripe's own emails cover a failed payment. The same run catches cancelled subscriptions. A paused bakery is blocked in three places: the storefront (`EnsureStorefrontEnabled` and `RootController` show `central.platform.bakery-paused` with a 503 for a KneadIt storefront; a bakery that uses its own website keeps its redirect), the tenant API (the `EnsureBakeryNotPaused` middleware on the `api` group in `routes/tenant.php` answers 403 `{"message": "This bakery is not currently accepting orders."}`, and deliberately does not look at `storefront_enabled`, so a running bakery on its own website keeps its API), and the customer-facing scheduled emails (birthday, repeat-order reminder, review request, abandoned-cart recovery and scheduled customer campaigns skip a paused bakery in `EngagementDispatcher`, `SendAbandonedCartRecoveryCommand` and `SendScheduledCampaignsCommand`; a skipped campaign stays scheduled and goes out after the bakery resumes; owner and staff emails such as low-stock alerts, the digest and billing mail still go). The bakery-admin panel stays open so the owner can still subscribe from the Upgrade Plan page. A bakery resumes (`ResumeTenant` clears `paused_at`) when the owner's subscription becomes valid: `StripeWebhookController` handles `customer.subscription.created` and `updated` with an `active` or `trialing` status through `StripeWebhookEventHandler::handleSubscriptionUpdated()`, and `CheckoutSuccessController` resumes it when it already sees a valid `default` subscription. Platform admins can also Pause or Resume a bakery from its Edit page and from the tenants table bulk actions (both `->authorize('platform-admin')`). When a subscription ends (`customer.subscription.deleted`, or an update to `canceled`, `incomplete_expired` or `unpaid`) and the owner has no other valid subscription, `ClearSubscriptionPlan` puts `tenants.plan` back to `starter`, the plan every new bakery starts on (the column is not nullable); `past_due` and `incomplete` keep the plan while Stripe retries. That does not pause the bakery; the trial-expiry run does. Free-forever tenants are excluded from both reminders and pausing (`TrialExpirationReader`). Free forever means Pro: every feature gate (the `growth-features` and `pro-features` Pennant flags, the navigation upgrade badges, the custom domain check and the Upgrade Plan page) reads `Tenant::effective_plan`, which is Pro for a free-forever bakery whatever `tenants.plan` holds. Granting free forever from the tenants table cancels the owner's subscriptions first (so the bakery is not billed as well). Extending a trial (`ExtendTenantTrial`, also behind the tenants table bulk action, which adds days to the current end and never shortens it) resumes a bakery that the trial's end had paused. A tenant with no linked owner gets no emails and is paused after its trial. Every owner ↔ bakery link uses `tenants.user_id`, never email: the trial job, the Stripe webhooks (`StripeCustomerLookupQuery` finds the user by `stripe_id`, then their bakery) and `CancelOwnerSubscriptionListener`, which cancels the owner's subscription when their bakery is deleted. A bakery with no linked owner gets no plan syncs and cancels nothing on delete. Only platform admins can manage bakeries (`TenantPolicy`), and `TenantPolicy::delete()` refuses a bakery whose owner has any `default` subscription that has not ended (every status except `canceled` and `incomplete_expired`, so past due, incomplete and unpaid ones count, and so does an older one behind a newer ended one; `OwnerSubscriptionsQuery::open()`) with "Cancel this bakery's subscription first." (the bulk delete reports it as a failure); the listener is a safety net behind it. The listener and the free-forever grant both call `CancelOwnerSubscriptions`, which cancels every open subscription: a healthy one at the end of the period already paid for, one that is past due, incomplete or unpaid immediately. The `has-plan` Gate (`SubscriptionTier::resolve()`) is available for per-plan features but nothing calls it yet; `resolve()` counts only a valid `default` subscription (active, trialing or on its grace period), so an ended one is not the current plan and the plans page offers checkout again. `CheckoutController` redirects back to the plans page when the owner already has a valid `default` subscription (use Switch to change plans), sends the owner to the Stripe billing portal when a past-due, incomplete or unpaid one is still open (a second subscription would double charge; the plans page shows the portal link whenever the owner has a Stripe customer), and starts the Stripe subscription with `trialUntil(tenants.trial_ends_at)` while the owner's bakery is still in its trial, so the first charge happens when the bakery trial ends; once that trial has ended (or there is no bakery) the subscription starts billing immediately. Signup is bakery first, but only for owners with a verified email: `RegisterController` sends a new owner to `verification.notice` (the "check your email" page, with Resend and a log out / use a different email button; the `bakery_name` and referral session values carry over) and the `onboarding.*` routes carry the `verified` middleware, so an unverified owner cannot create a bakery. The verification email is `OwnerVerifyEmailNotification` (signed and expiring, built from the central `app.url` with no bakery settings), rendered in the shared KneadIt email layout `emails.platform.layout`. That layout carries KneadIt's own logo, colours and footer and never reads bakery settings; an email fills its `title` and `content` sections and can use the `x-emails.platform.button`, `x-emails.platform.fallback-link` and `x-emails.platform.panel` components. Every `PlatformMail` (welcome, trial reminder and expiry, payment failed, contact form, campaign, check-in and the platform admin alerts) uses it; only the bakery-branded `StaffInvitationMail` and `WeeklyDigestMail` do not. `VerifyEmailController` then sends the owner to `onboarding.show`, or to the bakery admin when they already own a bakery. Only bakery creation is gated: billing, the billing handoff, the bakery admin and existing bakeries' owners do not require a verified email. `CreateTenantRecord` starts the trial, and the plans page, reached later through Manage billing, shows "Your free trial ends on {date}" and needs a card only when a plan is chosen. Outside `local` and `testing`, the `RequireStripeWebhookSecret` route middleware on `/stripe/webhook` refuses every event with a 500 while `cashier.webhook.secret` is empty, because Cashier only verifies signatures when a secret is set (the Connect webhook behaves the same way).
  **Owner billing handoff:** the Cashier subscription and the `/billing` pages live on the central user, but bakery owners sign in on their bakery host (the central login only admits platform admins), so they reach billing through a one-time handoff, the reverse of impersonation. The Upgrade Plan page's **Manage billing** action (and its Upgrade buttons) is shown only to the bakery owner role (`manage-billing` Gate) and only when `tenants.user_id` is set. It runs `CreateBillingHandoffToken`, which stores a row in the central `billing_handoff_tokens` table (SHA-256 hash of a 64-character token, the tenant id, the central owner `tenants.user_id`, a 2-minute expiry) and redirects to `TenantUrlGenerator::billingHandoff()`, a URL built from `app.url` (a `route()` call would be rewritten onto the bakery host under tenancy). `GET /billing/handoff/{token}` (`billing.handoff`, throttled with `sensitive-write`) runs `ConsumeBillingHandoffToken`: one conditional `UPDATE` claims an unused, unexpired token, the bakery's current `user_id` must still be the owner the token was issued for, and the controller then flushes the session, logs that central user in on the `web` guard and redirects to `billing.plans`. An unknown, used or expired token gets a 403 page that links back to the bakery admin when the token is known. The plans page shows which bakery it is for and a Back to your bakery link (`TenantUrlGenerator::admin()`); for a free-forever bakery it says the plan is complimentary, offers no plans, and `CheckoutController` refuses without calling Stripe. The `billing.*` routes sit behind `PreventAccessFromTenantDomains` (it runs before `auth`), so a request on a bakery host gets a 404 instead of failing on the central database. `TrialReminderMail`, `TrialExpiredMail` and `PaymentFailedMail` link to the bakery admin's Upgrade Plan page (`TenantUrlGenerator::billingForOwner()`), where the owner is already signed in; the link is left out when the account owns no bakery.
- **Storefront payments:** Stripe Connect charges bakery customers through the connected bakery account. The tenant's Connect account and payment toggle come from tenant settings.

For a positive-total order with Stripe enabled, `StripeCheckoutService` creates a connected-account Checkout Session, stores its session identifier, and redirects off-site. The success callback retrieves the session from Stripe and accepts only a paid session; `HandleCheckoutComplete` stores the payment intent and delegates the idempotent paid transition to `MarkOrderPaid`, but only when the session's `amount_total` equals the order total. A different amount leaves the order unpaid, stores the payment intent, logs a warning and sends the bakery owners a database notification (`ReportStripeAmountMismatch`); the success page then shows a "needs review" notice instead of "Payment successful". The webhook path goes through the same `HandleCheckoutComplete` action. The Connect webhook verifies its Stripe signature, records webhook delivery/idempotency, initializes the referenced tenant, and handles supported account or checkout events. `HandleConnectCheckoutCompleted` picks the bakery from the session's `metadata.tenant_id` and acts only when the event's own Connect `account` equals that bakery's stored `stripe_connect_id`; otherwise it logs a warning and does nothing. A cancelled checkout returns the order to unpaid status.

Checkout is cards only: the order and catering deposit sessions are created with `payment_method_types: ['card']`, so a delayed-settlement method (bank debit) can never leave a paid-looking session with no recorded payment. The order form posts with `fetch`, so `SubmitOrderController` answers a JSON request with `{"data": {"redirect_url": ...}}` (the Stripe URL, or the confirmation page with the success message flashed) and the page sets `window.location` itself; following a redirect to checkout.stripe.com cross-origin would fail and show an error for an order that exists. A plain form post still gets a redirect, and the Place Order button stays disabled while the browser navigates away. A customer who leaves Stripe without paying sees a Pay now button on the confirmation page (`StripeCheckoutService::canPayOnline()`: a Stripe order that is unpaid, not cancelled, with a positive total, while the bakery still takes cards). It posts to `order.pay` (`PayOrderController`), which calls `resumeOrCreateCheckout()`: the stored session's URL while Stripe reports it open, the success page when it turns out to have been paid, otherwise a new session (a finished session's id is cleared first, so `OrderModificationGuard::hasOpenCheckout()` does not block edits for good if no replacement can be made). The open session is expired (`ExpireStripeCheckout`, on the connected account, never inside a transaction and never failing the caller) when staff cancel an unpaid order (`CancelOrder`) and when `MarkOrderPaid` settles an order with no Stripe payment intent (cash, PayPal, Mark Paid); the stored session id is kept so a payment that still lands can be matched. `HandleCheckoutComplete` refuses to apply a Stripe payment to an order that is Cancelled, or already Paid with a different payment intent: the order and its recorded intent stay as they are, and `ReportLateStripePayment` logs a warning and notifies the bakery owners once per payment intent so they can refund it in Stripe. `MarkOrderPaid` re-reads the order under a row lock and does nothing when it is already paid, so the success redirect and the webhook racing each other both succeed.

Catering deposits use `CateringDepositCheckoutService` and the signed `catering.payDeposit` link from the quote email. Only a Quoted or Confirmed inquiry takes a deposit (`CateringInquiryStatus::acceptsDeposit()`); any other status shows a "no longer open for payment" page (410) and starts no checkout. The service keeps one live session per inquiry: it reuses the stored session's URL while Stripe reports it open, completes it if it was already paid, and creates a new one only after it expired. The success and cancel URLs are signed (the success route ignores the `session_id` parameter Stripe appends). Both completion paths, the success redirect and the Connect webhook, find the inquiry by `metadata.catering_inquiry_id`, not by the latest stored session id, and call `ApplyCateringDepositPayment`. That action re-reads the inquiry under a lock and records the deposit through `RecordCateringDeposit`; if the deposit is already recorded or the inquiry no longer takes deposits, it records nothing, logs a warning and notifies the bakery owners once per session so they can refund it by hand.

Orders can also use enabled non-Stripe methods. PayPal support creates and sends invoices and the production scheduler checks invoice payment status hourly (`paypal:check-payments`). The command resolves everything that depends on tenant settings (the settings manager, the PayPal token manager and client, `MarkOrderPaid`) inside each tenant's `forEachTenant` callback, so every bakery is polled with its own credentials and nothing reads tenant tables on the central connection. `tests/Feature/Console/ScheduledTenantCommandsTest.php` guards every scheduled tenant command against that mistake. Manual/cash flows proceed directly to confirmation. Refund behavior is payment-specific; Stripe refunds require a paid order and a captured payment-intent identifier, then record the refund transaction and transition payment status.

In the bakery-admin Filament panel, the order form shows `status` read-only and `payment_status` read-only on edit, so saving the form never changes either. Status changes go through the table and view-page actions that call `TransitionOrderStatus`, and payments received outside checkout are recorded with the Mark Paid actions that call `MarkOrderPaid`. Mark Paid is offered while `PaymentStatus::canBeMarkedPaid()` is true (Unpaid or Partial, so a catering order with a deposit can be settled) and the order isn't Cancelled. Send PayPal Invoice stays Unpaid-only because the invoice bills the full order total. An order created from the admin form starts Pending, and its total is computed on the server from the submitted amounts (`OrderForm::withComputedTotal()`). The money fields (subtotal, delivery fee, discount, gift card amount, tip and total) are read-only on edit, so they can't drift from the coupon and gift card ledgers; item changes re-price through `ModifyOrder`. `TransitionOrderStatus` re-reads the order with a row lock inside its transaction and checks the transition against that fresh status, so a double tap or second tab holding a stale copy is refused (`InvalidOrderTransitionException`) before it can send a second delivered email or webhook. Start Baking always succeeds: `AdjustIngredientStock` is called with `allowNegative`, the shortfall of each ingredient left below zero comes back as an `IngredientShortfall`, and `NotifyStaffOfNegativeStock` shows the person who pressed Start Baking a warning toast and sends every staff member a database notification naming them (`StockStatus::Negative` marks them on the ingredients table, the low-stock widget and the daily low-stock email). Each usage and restock row carries the `order_id` that caused it (`stock_adjustments.order_id`), and cancelling from Baking restocks the net of that order's recorded usage rather than recomputing from the current recipes, so a recipe edited or deleted after Baking restocks the right amount and a repeat restock puts nothing back. The driver page (`DriverDashboardController`, today from `BakeryClock`) lists Ready delivery orders only, and marking another status delivered redirects back with an error.

Cancelling goes through one action, `CancelOrder`, used by the shared `CancelOrderAction` on the orders table and the order page (the page's Change Status no longer lists Cancelled). A paid order with a Stripe payment intent is refunded first (`RefundStripePayment`) and cancelled only once Stripe accepts the refund; a refusal leaves the order untouched and shows an error. Double submits are guarded without holding a transaction across the Stripe call (SQLite would keep a read snapshot over the network call and then fail to write with "database is locked"). `RefundStripePayment` first claims the refund with one atomic conditional UPDATE that sets `orders.refund_claimed_at` only while the order is Paid and unclaimed; a request that updates no row never reaches Stripe, and either finds the order already refunded (returns nothing) or, if a live claim is held, gets `OrderRefundInProgressException`. It then calls Stripe with the idempotency key `refund-{order id}-{payment intent id}` and records the `Refund` row and the new payment status in a short transaction that clears the claim. A Stripe refusal clears the claim so a retry can proceed (Stripe replays a refusal for the same key for about 24 hours), and a claim older than 10 minutes is treated as abandoned and can be claimed again, where the idempotency key makes Stripe return the original refund. `CancelOrder` checks a fresh copy of the order before refunding, and `TransitionOrderStatus` re-reads the order under `lockForUpdate()` inside its own short transaction (no network call) and re-checks the transition, so a stale second cancel is refused. A paid order taken another way (PayPal, cash) is cancelled and stays Paid, with a notice that the customer must be refunded outside the app. `OrderPolicy::cancel()` lets Staff cancel only orders with no payment held (`PaymentStatus::holdsPayment()`: Paid or Partial); managers and above can cancel any order. `RefundOrderAction` (`OrderPolicy::refund()`, managers and above) refunds an order that is Cancelled but still Paid. On cancellation `ReverseOrderDiscounts` credits a gift card with the amount on the order's `Redemption` ledger row, not `orders.gift_card_amount`.

## Settings architecture

Settings are database-backed key/value records with separate tenant and platform managers:

- `SettingsManager` reads tenant `Setting` records in the current tenant database.
- `PlatformSettingsManager` reads central platform settings.
- `AbstractSettingsManager` memoizes primitive values in memory for the current manager instance and provides transactional bulk writes.
- "Reset to defaults" on `ManageSettings` leaves the integration settings (`TenantSettingsDefaults::integrationKeys()`: webhook URL and secret, PayPal credentials and sandbox flag) as they are, so a reset followed by Save cannot disconnect an integration.
- `TenantSettingCipher` transparently encrypts PayPal credentials and webhook signing secrets before persistence; tenant migrations encrypt legacy plaintext values without changing settings consumers.
- Webhook configuration is owner-only because payloads carry customer names and emails. The `manage-webhooks` Gate (Owner role and above) guards the Integrations section of `ManageSettings`, the Webhook Deliveries resource, the Webhook Docs page, and the Send Test, Regenerate Secret and Redeliver actions. For other roles `ManageSettings` never loads the webhook URL or secret into its public properties (Livewire would send them to the browser), refuses the test and regenerate methods with 403, and keeps the stored values on save.
- Payment credentials are owner-only and write-only. The `manage-payments` Gate (Owner role and above) guards the whole Payment Methods section of `ManageSettings` (accepted methods, Stripe Connect panel, PayPal client id, secret, sandbox flag and invoice terms), the `stripe.connect` route, and the onboarding Payments step, which saves nothing for other roles. The PayPal client secret is never loaded into a public Livewire property: its field always starts empty (the placeholder says a value is set) and a new value is written only when one is entered. For other roles the client id is not loaded either, and saving keeps the stored payment methods, credentials and invoice terms whatever the client sends. There is no generic key/value settings page; every setting is edited through a typed form.
- `TenantSettings` is a read-only composite DTO of typed settings groups such as store, branding, orders, payments, catering, loyalty, policies, homepage, webhooks, gift cards, and inventory.
- `TenantSettingsDefaults` supplies defaults used when provisioning or resolving unset values.

Controllers should receive the typed `TenantSettings` DTO when rendering storefront data. Write paths use the relevant action plus `SettingsManager`. Tenancy transitions flush the manager cache, preventing values from one bakery surviving into another tenant context.

Central onboarding screens read denormalized product, category, and order counts from the tenant record instead of opening every tenant database during a web request. `tenants:sync-onboarding-metrics` reconciles those counts every fifteen minutes and should be run once immediately after deploying its central migration.

The onboarding subdomain doubles as the tenant id and the bare domain row, so `StoreOnboardingRequest` lowercases and trims it before validating, requires a valid hostname label, rejects `config('kneadit.reserved_subdomains')`, and checks uniqueness against both `domains.domain` and `tenants.id`.

Tenant onboarding is coordinated by `CompleteTenantOnboarding`. `CreateTenantRecord` owns the central tenant/domain transaction, `ProvisionTenantOwner` seeds the tenant owner and settings inside tenant context, and `CreateTenant` provides compensating cleanup if provisioning fails. The orchestrator then completes any referral and emits `TenantOnboarded`; the HTTP controller retains only session logout/rotation and redirect concerns.

An account owns at most one bakery. `CreateTenantRecord` writes the owner to `tenants.user_id` and refuses a user who already has a bakery with `UserAlreadyHasBakeryException`; the unique index on `tenants.user_id` enforces the rule under concurrent submissions (a unique violation is treated as the same outcome). `GET /onboarding` redirects an owner to their bakery admin via `TenantUrlGenerator::admin()`, and `POST /onboarding` redirects there with an error flash. Tenants without an owner (demo, browser-test and seed tenants, and tenants created in the central admin) leave `user_id` NULL, which the index allows.

Inside the bakery admin, `EnsureOnboardingComplete` sends every signed-in user to the `Onboarding` page (`/admin/onboarding`) until the `onboarding_completed_at` setting is set. The wizard's steps (`app/Filament/Pages/Platform/OnboardingSteps/`) save their settings as each step validates; the Branding step reads the logo from the step schema's validated state (so a new upload is stored and an existing path is only accepted if it is the bakery's current logo). Completing the wizard, or importing a bakery with `DatabaseLegacySettingsImporter` (an imported bakery is already set up; an existing value is kept), sets the flag. The Stripe status shown on the Payments step and in Settings comes from `StripeSettingsReader::connectStatus()` (`StripeConnectStatus`: not connected, connected with charges not enabled yet, charges enabled), which reads `stripe_connect_id` and `stripe_connect_charges_enabled`.

## Email marketing and unsubscribe

Customers can opt out of marketing email. `customers.marketing_opted_out_at` (null = subscribed) is set by the customer from the unsubscribe link in any marketing email, or by staff through the Customers table's "Mark unsubscribed" action (for opt-outs received by phone or email). Staff cannot re-subscribe a customer; only the customer can, from the same link.

**Marketing mails** (a message the customer did not specifically ask for) implement `MarketingMail` and use `SendsMarketingMail`:

- `CustomerCampaignMail` (customer campaigns) and `BulkCustomerMessageMail` (the Customers "Send message" bulk action when its purpose is Promotion).
- The automated engagements: `HappyBirthdayMail`, `RepeatOrderReminderMail`, `ReviewRequestMail`, and `AbandonedCartRecoveryMail`.

**Transactional mails** are never suppressed and carry no unsubscribe link: order placed, status, modified and messages, `OrderUpdateMessageMail` (the "Send message" bulk action when its purpose is Order update), order tracking links, catering quotes, product-available alerts (the customer asked to be told), referral rewards (earned) and contact-message replies. Staff, supplier and platform notifications are not customer marketing either. For a new customer-facing mail, decide by asking whether the customer requested that specific message.

Every marketing mail sends `List-Unsubscribe` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` (RFC 8058) and shows an "Unsubscribe" link in the shared email layout. `BaseMailable` passes `unsubscribeUrl` to the view for any `MarketingMail`. `MarketingUnsubscribeLinks` builds the link: a non-expiring URL signed against its path only (`signed:relative`) and prefixed with the bakery's storefront host, so it works from queued or scheduled sends where the request host is not the bakery's.

The Customers "Send message" bulk action makes the baker choose a required `BulkMessagePurpose` (no default), so the opt-out cannot be bypassed by accident. `SendBulkCustomerMessage` takes the enum and returns a `BulkMessageOutcome` (sent, skipped for no email, skipped as ineligible) that the notification summarises, for example "3 sent; 2 skipped (no open order)". **Order update** is transactional: it goes to selected customers with an open order (`CustomerQueryBuilder::withOpenOrder()`: pending, confirmed, baking or ready), including those who unsubscribed, and sends `OrderUpdateMessageMail` with no unsubscribe headers or footer link. **Promotion** keeps the marketing behavior: `BulkCustomerMessageMail`, opted-out customers skipped.

`EmailUnsubscribesController` serves the link (routes in `routes/tenant/access.php`, outside the storefront-enabled check): `GET` shows a confirmation page, `POST` unsubscribes immediately and is CSRF-exempt because mail providers post without a token (the signature is the protection), and `DELETE` re-subscribes from the confirmation page.

Senders skip opted-out customers in the query (`CustomerQueryBuilder::subscribedToMarketing()`), so recorded recipient counts exclude them: `ResolveCampaignRecipients`, `SendBulkCustomerMessage` (promotions only), the three engagement recipient finders and `SendAbandonedCartRecoveryCommand`. Platform email campaigns go to bakery owners, not customers, so they are not customer marketing. The birthday, repeat-order and review-request listeners re-check just before sending. Abandoned-cart recovery (`CartQueryBuilder::forRecoverableCustomers()`) only mails a cart saved from a signed-in customer session (`carts.customer_id`, set by `CartManager::updateContact()`, which then takes the email and name from the customer record and ignores what the browser sent) or a guest cart whose email belongs to a customer who verified it, and always to a customer who has not unsubscribed, because the opt-out lives on the customer record. The mail is sent to the customer record's email and greets its stored name, never the name typed into the cart.

Engagement product rules. Turning on review requests or cart recovery does not email the backlog: `ReviewRequestEngagement` only considers orders delivered (last updated) between `review_request_delay_hours` and that delay plus 7 days ago, and sends one request per customer per run, for their most recent eligible order, marking that customer's other eligible orders as handled so they do not trickle out later; `SendAbandonedCartRecoveryCommand` only mails carts with activity in the last 7 days that have not passed `expires_at` (`CartQueryBuilder::activeSince()` and `notExpired()`). `BirthdayEngagement` celebrates a Feb 29 birthday on Feb 28 (bakery-local) in a non-leap year. Loyalty points are credited on delivery by `LoyaltyLedger::creditOrder()`, which reads the stored payment status and skips an order that is already Refunded or Cancelled (`PaymentStatus::earnsLoyaltyPoints()`), so a refund that lands before a queued award leaves no points; a full refund takes them back with `LoyaltyLedger::reverseOrder()`, which writes one `Reversed` ledger row (positive magnitude, subtracted by `LoyaltyBalance`) holding the points the order's `Earned` row holds, unique per order and type like the credit. It runs from `RefundStripePayment` and from the PayPal payment check when an invoice comes back refunded (the only paths that set an order to Refunded; the order form's payment status is editable on create only). Tiers and tier perks (`CustomerLoyalty`) use `LoyaltyBalance::netEarned` (earned minus reversed), so a refunded order no longer counts toward a tier. A balance that goes negative because the points were already redeemed is shown as is, and there is no partial-refund path, so a partial refund never reverses points.

## Personal data and the activity log

`LogsActivityObserver` writes a row to `activity_logs` when an observed model is created, updated or deleted. The row keeps `user_id` only when that user exists in the current database; otherwise (for example the central owner while a bakery is being set up) it stores a null `user_id` and the actor's name. Updates store the changed attributes, passed through `ActivityLogRedactor`: a model's hidden attributes (`getHidden()`) and the keys `password`, `*_token`, `*_secret` and `two_factor_*` are recorded as changed with the value `[redacted]`. `activity-log:redact-secrets` applies the same rule to rows written earlier (run it once per deploy of this change; it walks every tenant and is safe to repeat). `activity-log:prune` deletes rows older than 365 days (`--days`), daily, per tenant.

Erasing a customer. `AnonymiseCustomer` (the Anonymise action on the Customer page, Manager role or above through `CustomerPolicy::anonymise()`) keeps the customer row and their orders for accounting but replaces the name, email (`deleted+{id}@invalid`), phone, address, birthday and notes, sets a password nobody knows (so signed-in sessions end at their next request, see `AuthenticateCustomerSession`), clears the remember token, unsubscribes the customer from marketing and deletes their `customer_profiles` row, staff `customer_notes` and `customer_reminders` (loyalty points and referrals stay tied to the customer id for accounting). `EraseCustomerPersonalRecords` handles what is not tied to the customer by a foreign key, matching on the email: favorites, campaign logs, product and date waitlists, photos (and their files), survey responses and carts (also by `carts.customer_id`) are deleted; a review is kept without the reviewer's name, email and photo only if it was approved, otherwise deleted; catering inquiries keep their row but lose the contact name, email and phone and their free text (`details` becomes `[removed]`; dietary requirements, venue address and notes are emptied); a survey response filed against one of the customer's orders but not under their email keeps its row without name, email and answers. It also redacts the customer's values (and those of the reviews and inquiries it touched) in the activity log. `CustomerObserver::deleted()` runs the same clean-up when a customer without orders is deleted. Orders keep their own delivery address, notes and pickup contact fields.

## Frontend

Blade, Livewire, Alpine.js, Filament, and Tailwind CSS make up the UI. Vite builds separate central/application, storefront, tenant Filament, and central Filament entry points defined in `vite.config.js`. Inline scripts and styles use the request-scoped CSP nonce directive.

### Admin theming

Both Filament panels (bakery admin `AdminPanelProvider`, platform `CentralPanelProvider`) take their look from the KneadIt design system through `App\Filament\Shared\DesignSystem::configure()`: Instrument Sans as the panel font, Young Serif as the display face (both from Google Fonts), the honey, danger, success, warning, info and warm gray palettes, and dark mode support. Both panels then call `DesignSystem::lightByDefault()`: dark mode is not forced, the default theme mode is Light, and the user menu shows the Light / Dark / System switch. There is no per-bakery or per-platform theme picker; the old Honey / Slate / Nord presets, `PanelThemes` and the `admin_theme` / `central_theme` readers are gone (stored `admin_theme` setting rows are left in place and ignored).

`resources/css/kneadit/tokens.css` defines every design token as a `--kn-*` CSS variable: light values on `:root`, dark values under `.dark` (the class Filament puts on `<html>`). Use `--kn-*` variables in new CSS, never raw hex. Both panel themes import it, plus `kneadit/filament.css` (page headings in the display face, primary buttons in honey with the `--kn-on-honey` warm-black text, because Filament's own button text would be white on honey) and `kneadit/admin-aliases.css`. The aliases keep the older `--brand-*` and `--border-subtle` names as role-based mappings onto the tokens so they follow the light/dark switch; the admin partials no longer read them. What still does: the Tailwind `bg-brand-*` / `text-brand-*` utilities in tenant admin Blade views (through the `@theme` block in `filament/admin/theme.css`), the dashboard-config page, and the widget preview component (also rendered by the platform widget catalog, which is why the central theme imports the aliases too). The platform admin theme (`filament/central/theme.css`) is the same shell as the bakery admin: it imports the admin partials directly and adds only `filament/central/_chrome.css` (the profile block in the user menu); it defines no variables of its own, and `public/css/central-admin.css` and the `--platform-*` / `--accent` aliases are gone. Every admin partial (`_layout`, `_chrome`, `_forms`, `_tables`, `_modals`, `_notifications`, `_widgets`), the shared widget cards (`filament/shared/widget-cards.css`, also used by the central panel) and `kneadit/filament.css` style Filament with `--kn-*` directly, in both themes and with no `!important`: Filament's own component styles are in `@layer components`, so unlayered rules win without it (`tests/Unit/Resources/AdminLayoutStylesheetsTest.php` enforces no `!important`, no hex or rgb colours and no white text in those files and in `filament/central/_chrome.css`, and that every alias still in `admin-aliases.css` is used). Table, modal, notification and stat styles follow the brand book: `surface` cards with a `border` hairline, status badges as the status colour on its `-tint`, destructive buttons `--kn-danger` on `--kn-on-danger`. Blade views use token classes (`bg-(--kn-surface)`, `text-(--kn-ink)`, `text-brand-50` for ink) rather than `text-white`, `bg-white` or the old dark-only platform colour names; the platform views (`resources/views/filament/central`, `components/central`) follow the same rule, enforced by `tests/Unit/Resources/AdminThemedViewsTest.php`, except the previews of customer-facing output (email, announcement banner, search result), which keep the fixed colours the customer sees; `x-tenant-admin.card` is a `.tenant-admin-card` surface. Chart.js datasets in the dashboard chart widgets keep a fixed hex colour as the first paint and name a design-system token in a `colorToken` key (for example `--kn-honey`); the shared `x-filament.widgets.themed-chart` component (`knThemeChart`) repaints each dataset with that token's value once the chart exists and again on Filament's `theme-changed` event, because the canvas cannot read CSS variables. The chart's grid, text and tooltip colours come from the `.fi-wi-chart-*-color` elements in `_widgets.css`. Every table's filter button uses `FiltersTriggerAction` (set globally in `AppServiceProvider` with `Table::configureUsing`), which leaves the badge off while no filter is set; Filament would otherwise show a "0" badge. The platform analytics page instead reads the tokens in its script with `getComputedStyle` (for datasets as well) and redraws on Filament's `theme-changed` event.

### View organization

Blade views are organized by the application surface they serve:

- `resources/views/central/` contains central application views, grouped into `auth`, `billing`, `blog`, `legal`, `marketing`, `platform`, and `seo`.
- `resources/views/tenant/` contains tenant-facing views. `storefront/` holds public bakery pages and customer account flows, while `admin/` and `invitations/` hold tenant administration and staff invitation views.
- `resources/views/components/` contains reusable Blade components. Storefront home components live under `storefront/home`, and tenant administration components live under `tenant-admin`; their Blade tags and PHP component namespaces mirror those paths.
- `resources/views/shared/` contains cross-page includes that are not tied to a single surface, such as analytics and storefront order-form scripts.
- `resources/views/filament/`, `emails/`, `errors/`, `vendor/`, and `reference/` remain specialized top-level trees for their respective rendering contexts.
- The 401, 402, 403, 419 and 429 pages in `errors/` are one-line views around `components/error-page.blade.php`, which links `public/css/errors.css` (Laravel's default error views use an inline `<style>` that the CSP nonce policy blocks). Their copy lives in `lang/en/errors.php`; the 404, 500 and 503 pages keep their own views.

When adding a view, choose its location from the request surface first, then its feature. A view used by tenant models belongs under `tenant/` even if the controller is currently grouped in a central namespace. Component PHP classes and component integration tests should mirror the component's `resources/views/components/` path.

## Cross-cutting constraints

- Authorization belongs in policies, gates, and route middleware. Protected Filament actions require server-side authorization.
- Tenant-bound work must be executed only after tenancy initialization; queued work relies on the tenancy queue bootstrapper.
- Stable domain states use backed enums and model casts.
- Writes are transactional where multiple records or counters must remain consistent.
- Cache values must be scalars or primitive arrays; Eloquent objects are intentionally rejected by the configured serialization guard. Dashboard widgets cache plain arrays through `CachesWidgetData::cached()` (a DTO is cached as `toArray()` and rebuilt with `fromArray()`, `Money` as cents, models as arrays of their fields); tests can call `useSerializingCache()` to make the array store serialize like production and prove a cache hit still renders.
- Order URLs bind `{order:order_number}` rather than database IDs.
